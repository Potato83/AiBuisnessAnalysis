# AI-модуль — День 2

Простой синхронный конвейер: **валидация → ранжирование → один клиент → проверка структуры/ссылок → JSON и trace**. Агентного фреймворка, RAG, БД и автономной самопроверки пока нет. Комментарии в коде обозначают границы и места дальнейшей доработки.

```python
from backend.agent import generate_insights
result = generate_insights(company_profile, news, bank_sources)
```

Режим берётся из `backend/agent/.env`, затем переопределяется окружением процесса или аргументом `mode`. В локальном `.env` выбран `llm`; без файла и переменной `AGENT_MODE` используется mock. Текущая модель — DeepSeek-V4.1-Flash через API Mira. Результат проверки подключения: [APIMIRA_CHECK_REPORT.md](APIMIRA_CHECK_REPORT.md). GitHub и публикация ожидают отдельной команды пользователя.

## Установка и локальные проверки

Python 3.12, Pydantic 2.14.1, python-dotenv 1.1.1. Команды выполняются из корня проекта:

```sh
python -m pip install -r backend/agent/requirements.txt
python -m unittest discover -s tests -v
python -m backend.agent.examples --mode mock
python -m backend.agent.examples --mode mock --output data/synthetic/agent_day2_mock_results.json
```

Вывод — JSON-массив из двух результатов по восемь новостей. В нём `mode="mock"`, `model=null`, `is_mock=true`, уверенность `low` и предупреждение о синтетическом входе. Это не проверка реальной LLM. ID и время генерируются заново, содержание mock и порядок при одинаковом входе воспроизводимы.

## Вход

`company_profile` — обычный словарь. Обязателен строковый `id`. Необязательные поля:

- `name`, `industry_code`, `industry_name`, `region` — строки или null;
- `revenue_rub` — годовая выручка в рублях, неотрицательное десятичное число **строкой**;
- `debt_rub` — сумма кредитного долга в рублях, также строкой; дата оценки должна быть согласована поставщиком;
- `has_loans`, `has_deposits`, `has_foreign_trade` — bool или null;
- `operating_regions`, `counterparty_ids` — списки строк.

Неизвестный флаг — null, а не false. Долг/выручка — ориентировочное отношение, не показатель обслуживания долга и не вывод о плавающей ставке. ORM/CSV преобразует вызывающий компонент; неизвестные поля и строковые bool отклоняются.

`news` — список объектов с `id`, `title`, `text`. Дополнительные поля: HTTP(S) `url`, `published_at` с часовым поясом, `is_synthetic`, `event_type`, `industry_codes`, `regions`, `company_ids`.

Типы событий: `key_rate_unchanged`, `credit_conditions`, `deposit_conditions`, `industry_demand`, `regional_disruption`, `regulation`, `counterparty_event`, `fx_change`, `other`. Метки и отраслевую/региональную привязку передаёт news-компонент. Классификации сырого текста или скрытых совпадений по подстрокам здесь нет. Без достаточных меток оценка может быть unknown.

`bank_sources` — список с `id`, `title`, `text`, необязательными `url`, `published_at`, `is_synthetic`, `verified` и `related_news_ids`. Идентификаторы новостей и банковских материалов должны быть уникальны между списками.

### Правило bank_view

Позиция банка появляется только из связанного процитированного материала, для которого одновременно заданы:

1. `verified=true` — явное подтверждение происхождения поставщиком данных;
2. `is_synthetic=false`;
3. HTTP(S) URL;
4. ID текущей новости в `related_news_ids`.

`bank_view` копирует исходную выдержку с названием материала. LLM не генерирует это поле. При отсутствии подтверждённого материала значение **null**. Неподтверждённые и синтетические банковские тексты не отправляются в LLM. Флаг verified — входная аттестация Data/Backend, а не независимая проверка автора документа нашим модулем.

В демо Дня 2 `bank_sources=[]`, поэтому весь bank_view равен null. Банковские выдержки в unit-тестах — исключительно тестовые подмены.

## Ранжирование rules-v1

| Фактор | Баллы |
|---|---:|
| Прямое упоминание ID компании | 60 |
| Упоминание известного контрагента | 50 |
| Совпадение ОКВЭД или двухзначного раздела | 35 |
| Совпадение региона регистрации/операций | 40 |
| Кредиты при событии о ставке/финансировании | 40 |
| Положительный долг при неизвестном кредитном флаге | 40 |
| Долг/выручка менее 0.5 или от 0.5 | 5 или 10 |
| Депозиты при событии о ставке/депозитах | 25 |
| ВЭД при валютном событии | 35 |

Сумма ограничена 100. `high` — от 40; `medium` — 20–39; `low` — ниже 20 при наличии пригодных для сравнения признаков; `unknown` — нет оснований для оценки. Явное несовпадение или false может дать фактор с нулём баллов. Это прозрачная эвристика, не вероятность и не обученный ML-ranker. Веса нужно оценивать на размеченных примерах позднее.

Сортировка по убыванию баллов, при равенстве сохраняется входной порядок. Возвращаются все новости, включая low/unknown. Модель получает предварительное ранжирование и не меняет итоговые баллы или порядок. Для поиска материалов понадобятся инструменты Retrieval, принадлежащие Data Engineer.

## Результат и trace

Функция возвращает JSON-совместимый **dict**, не JSON-строку. Корневые поля: `schema_version`, `mode`, `model`, `company_id`, `agent_run_id`, UTC `generated_at`, `items`, `total`, `warnings`, `trace`.

Каждый insight сохраняет поля из `docs/API_CONTRACT.md`: `id`, `company_id`, `event_id`, `headline`, `why_relevant`, `impact`, `risks`, `opportunities`, `bank_view`, `ai_interpretation`, `confidence`, `sources`, `agent_run_id`, `generated_at`.

Дополнения: `facts`, `relevance`, `relevance_score`, `rank`, `reasons`, `source_ids`, `is_mock`, `trace`. Facts — переданное описание новости, без независимой фактологической проверки. ID insights временные; постоянные ID и дедупликацию нужно согласовать с хранением.

Trace каждого insight содержит использованные значения полей компании, факторы ранжирования с баллами, ID источников и этапы выполнения. Trace запуска содержит порядок новостей, попытку LLM, причину fallback, исключённые банковские материалы и usage/provider_model, если они получены от API. При ошибочном LLM-ответе токены могут быть потрачены без успешного результата; локальный trace такой ошибки не заменяет биллинг провайдера.

```python
from backend.agent.models import InsightInput, InsightDraft, InsightResult
input_schema = InsightInput.model_json_schema()
draft_schema = InsightDraft.model_json_schema()
output_schema = InsightResult.model_json_schema()
```

Схема и ссылки проверяются локально. Это не смысловая самопроверка: достоверность документа, достаточность доказательств для каждого риска и противоречия в выводах требуют Дня 3 и ручной оценки.

## Режимы и fallback

```python
# Явное локальное тестирование, без сети.
result = generate_insights(company_profile, news, bank_sources, mode="mock")

# Реальная LLM; отсутствие ключа, HTTP-ошибка или невалидный ответ дают исключение.
result = generate_insights(company_profile, news, bank_sources, mode="llm")

# Только при явном согласии вызывающего кода: целая пачка заменяется mock.
result = generate_insights(company_profile, news, bank_sources,
                           mode="llm", fallback_to_mock=True)
```

Fallback имеет `mode="mock"`, `model=null`, `is_mock=true`, предупреждение FALLBACK, `trace.attempted_mode="llm"` и тип ошибки. Ошибки не маскируются как успешная LLM-генерация. Без fallback ошибки передаются вызывающему коду. Входные ошибки и запрещённые модели не являются поводом для скрытой подмены.

Можно передать свой `client=...`, реализующий `InsightClient`: mode, разрешённое model_name и generate(request). Результат клиента — список черновиков/JSON-массив либо GenerationBatch с usage. Проверка model_name ограничивает выбор списком кейса. Единственный сетевой адаптер сейчас — DeepSeek-V4.1-Flash/API Mira.

## Настройка DeepSeek-V4.1-Flash через API Mira

Модель: `DeepSeek-V4.1-Flash`; API ID: `deepseek/deepseek-v4.1-flash`; базовый адрес: `https://apimira.com/v1`. Запрос отправляется в `/chat/completions`. Формат совместим с предоставленным примером OpenAI SDK; сам SDK не требуется, адаптер использует HTTP из стандартной библиотеки Python.

Локальный файл **`backend/agent/.env` уже создан**. Вставьте ключ в строку `APIMIRA_API_KEY=` внутри этого файла. После клонирования проекта создайте `.env` из соседнего `.env.example`, поскольку файл с ключом игнорируется Git.

```dotenv
AGENT_MODE=llm
APIMIRA_API_KEY=
APIMIRA_BASE_URL=https://apimira.com/v1
APIMIRA_MODEL=deepseek/deepseek-v4.1-flash
AGENT_LLM_TIMEOUT_SECONDS=180
AGENT_LLM_MAX_TOKENS=6000
AGENT_LLM_TEMPERATURE=0.5
AGENT_LLM_TOP_P=1
```

После получения ключа, из корня проекта:

```powershell
python -m backend.agent.examples --mode llm --output tmp/agent-day2-llm.json
```

`.env` загружается автоматически по пути модуля, независимо от текущего каталога. Переменные процесса имеют приоритет, включая пустые значения; загрузчик не меняет `os.environ`. Без ключа режим `llm` выдаёт `LLMConfigurationError` до сетевого запроса. Для проверки без ключа укажите `--mode mock` или `mode="mock"`. Файлы других компонентов и их настройки не нужны для локального Python-вызова агента.

Значения модели и базового URL проверяются: адаптер поддерживает выбранную DeepSeek через API Mira. Для смены провайдера нужна отдельная доработка. По умолчанию timeout=180 секунд, max_tokens=6000; лимит больше 1024 из краткого примера, поскольку демо запрашивает восемь интерпретаций за один вызов. Таймаут 180 секунд оставлен для длинных пачек. Параметр reasoning_effort от прежнего провайдера не передаётся. Контекст ограничен 60000 символами до отправки, ответ — 4 MiB. Автоматических повторов нет. Для backend-контейнера DevOps позднее должен передать переменные окружения: локальные `.env` исключены из Docker-контекста.

JSON запрашивается инструкцией с JSON Schema; Pydantic проверяет структуру после ответа. Шлюз API Mira отклоняет `response_format`, поэтому этот параметр не передаётся. Ответ LLM должен иметь обёртку `{"items":[...]}`. Адаптер проверяет черновики, выбранную модель, завершённость ответа и usage. Отдельное `reasoning_content` не сохраняется в JSON/trace. Ошибки: LLMConfigurationError, LLMTransportError, LLMResponseError. HTTP 401/429/503 не превращаются в выдуманные инсайты.

Для проверки настоящей LLM **не включайте** `--fallback-mock`: так ошибка не будет принята за успешное подключение. Затем убедитесь в `mode=llm`, правильном provider_model, расходе токенов, разных интерпретациях одной новости и корректном bank_view=null. Качество содержания оценивается вручную. Полноценный автономный цикл остаётся на День 3.

Официальная документация: [API Mira](https://apimira.com/docs).

## Демо и границы ответственности

`data/synthetic/agent_day2.json` содержит две вымышленные компании и восемь вымышленных новостей: ставка, промышленность, оптовая торговля, два региона, контрагент, валюта и депозиты. Обе компании имеют выручку свыше 15 млрд рублей. Полученные mock-результаты сохраняются отдельно в `agent_day2_mock_results.json` и не выдаются за результат реальной модели.

Backend нормализует профиль, вызывает функцию и решает вопросы HTTP/хранения. Data подтверждает происхождение банковских материалов, передаёт ОКВЭД, долговые показатели, регионы и контрагентов; News передаёт тип события и метки. Retrieval/поиск и таблицы модуль AI не реализует. Синхронный LLM-вызов нужно выполнять вне async event loop.

Для интеграции Backend нужно установить `backend/agent/requirements.txt`, включить Python-пакет `backend/agent/` в сборку и передать переменные `APIMIRA_*` в процесс сервера. Docker/Compose и общие зависимости в PR агента не меняются: эти изменения выполняет владелец Backend/DevOps. Секретный `.env` в образ не копируется.

Пример успешной реальной генерации на синтетических данных сохранён в `data/synthetic/agent_day2_llm_results.json`; маркировка `is_synthetic` и trace сохраняются.

День 3: один агент с состоянием выполнения — план → вызов инструментов → контекст и доказательства → анализ → самопроверка → ограниченный повтор поиска → сохранение trace и результата. Количество шагов/повторов и бюджет должны быть ограничены; готовая мультиагентная система не требуется.
